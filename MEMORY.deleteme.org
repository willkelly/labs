** Q1: SQLite Read/Write Connection Management

*** The Comment in Question

File: [[file:packages/memory/memory.ts::67][packages/memory/memory.ts:67-76]]

#+begin_src typescript
/**
 * Runs task one at a time, this works around some bug in deno sqlite bindings
 * which seems to cause problems if query and transaction happen concurrently.
 */
async perform<Out>(task: () => Promise<Out>): Promise<Out> {
  return await traceAsync("memory.perform", async (_span) => {
    const result = this.ready.finally().then(task);
    this.ready = result.finally();
    await this.ready;
    return await result;
  });
}
#+end_src

*** The Verdict: NOT A BUG

*This is SQLite's correct behavior*, not a bug in the Deno SQLite library.

*Why?*
1. SQLite allows *multiple concurrent reads* but only *ONE write transaction at a time*
2. You *cannot* mix reads and writes concurrently on the *same database connection*
3. This limitation exists in ALL SQLite implementations (C API, Python, Rust, etc.)
4. The =perform= queue is a reasonable workaround given single-connection architecture

*** SQLite's Concurrency Model

#+begin_example
┌────────────────────────────────────────┐
│   SQLite Concurrency (Default Mode)   │
├────────────────────────────────────────┤
│ Multiple Readers:    ✓ Supported      │
│ Multiple Writers:    ✗ NOT supported  │
│ Reader + Writer:     ✗ Blocks         │
│ Same Connection:     ✗ Serialized     │
└────────────────────────────────────────┘

┌────────────────────────────────────────┐
│   SQLite Concurrency (WAL Mode)       │
├────────────────────────────────────────┤
│ Multiple Readers:    ✓ Supported      │
│ Multiple Writers:    ✗ Still only ONE │
│ Reader + Writer:     ✓ Concurrent     │
│ Same Connection:     ⚠ Complex         │
└────────────────────────────────────────┘
#+end_example

*** Recommendation

*DO NOT REMOVE* the =perform= queue without implementing a read connection pool with WAL mode.

*UPDATE* the comment to accurately describe the behavior:

#+begin_src typescript
/**
 * Serializes database operations to prevent conflicts on a single connection.
 *
 * SQLite allows multiple concurrent readers OR one writer, but mixing reads
 * and writes on the same connection causes lock contention. To enable true
 * concurrent access, we would need to:
 * 1. Enable WAL mode (PRAGMA journal_mode = WAL)
 * 2. Implement a read connection pool
 * 3. Separate read and write code paths
 *
 * See: https://www.sqlite.org/lockingv3.html
 */
#+end_src

** Q3: WAL Mode and Read Pools

*** Current Architecture

Each "space" is a separate SQLite database file:
- File: [[file:packages/memory/memory.ts::232][packages/memory/memory.ts:232-234]]
- Pattern: =./${subject}.sqlite=
- Connection: Single connection per space, all operations serialized

*** WAL Mode Benefits

*Write-Ahead Logging* would provide:

1. *Concurrent Reads*: Multiple readers can read while a writer writes
2. *Better Performance*: Fewer disk syncs, better I/O patterns
3. *No Reader Blocking*: Readers never block on writers or other readers

#+begin_example
Without WAL (Current):
  Operation Queue: [Query1] → [Transact1] → [Query2] → [Transact2]
                   (fully serialized)

With WAL + Read Pool:
  Read Pool:   [Query1, Query2, Query3, ...] (parallel)
       ↕
  Write Conn:  [Transact1] → [Transact2] → ... (serialized)
#+end_example

*** WAL Mode Limitations

1. *Network Filesystems*: WAL requires all connections on same host (not NFS/CIFS)
2. *File Count*: Creates 3 files (=.db=, =.db-wal=, =.db-shm=) instead of 1
3. *Unbounded Growth*: WAL can grow if readers never finish
4. *Checkpoint Management*: Requires periodic WAL→DB flushes

*** Read Pool Requirements

The =@db/sqlite= library has *NO built-in connection pooling*. Would need:

#+begin_src typescript
class ConnectionPool {
  private readConnections: Database[] = [];
  private writeConnection: Database;

  async acquire(): Promise<Database> {
    // Implement acquire/release pattern
  }

  async release(conn: Database): Promise<void> {
    // Return to pool
  }
}
#+end_src

*** Usage Pattern Analysis

From test suite analysis:
- *182 total operations* across all tests
- *Estimated 60-70% reads, 30-40% writes*
- Read-heavy workload would benefit significantly

*** Recommendation

*Phase 1*: Enable WAL mode (low risk)

// Skip for :memory: databases

  database.exec("PRAGMA journal_mode = WAL;");
}
#+end_src

*Phase 2*: Implement read connection pool (medium risk)
*Phase 3*: Refactor to separate read/write paths (high risk)

See [[file:REPORTS/q3-wal-mode-and-read-pools.org::*Implementation Recommendations][detailed implementation plan]] in Q3 report.

** Q4: Understanding the Fact/Datum System with Shopping List Example

*** Core Data Model

The system uses a four-field model:

| Field   | Meaning                           | Example                               |
|---------+-----------------------------------+---------------------------------------|
| =the=   | MIME type of fact                 | ="application/json"=                  |
| =of=    | Entity identifier                 | ="of:bafyreiabc123..."=               |
| =is=    | JSON value (or undefined)         | ={items: ["milk", "bread"]}=          |
| =cause= | Reference to previous fact        | ={"/": "bafyreigxyz..."}=             |

*** Three-Table Architecture

#+begin_example
┌─────────────────────┐
│  datum              │  ← Deduplicated JSON values (content-addressed)
├─────────────────────┤
│ this (PK)           │  Merkle reference (hash of value)
│ source (JSON)       │  The actual JSON data
└─────────────────────┘
         ▲
         │ Foreign Key: fact.is → datum.this
         │
┌─────────────────────┐
│  fact               │  ← Complete history (append-only log)
├─────────────────────┤
│ this (PK)           │  Merkle reference of {the, of, is, cause}
│ the                 │  MIME type
│ of                  │  Entity ID
│ is (FK)             │  → datum.this or "undefined"
│ cause               │  → Previous fact reference
│ since (Lamport)     │  Logical clock for ordering
└─────────────────────┘
         ▲
         │ Foreign Key: memory.fact → fact.this
         │
┌─────────────────────┐
│  memory             │  ← Current state only (constant size)
├─────────────────────┤
│ the (PK)            │  MIME type
│ of (PK)             │  Entity ID
│ fact (FK)           │  → Latest fact
└─────────────────────┘
#+end_example

*** Concurrent Updates and CAS

*Scenario:* Alice and Bob both try to add items simultaneously.

Alice's transaction:
#+begin_src typescript
assert: {
  is: { items: ["milk", "bread", "eggs"] },  // Alice adds eggs
  cause: { "/": "bafyreistep3..." }          // Based on Step 3
}
#+end_src

Bob's transaction:
#+begin_src typescript
assert: {
  is: { items: ["milk", "bread", "cheese"] },  // Bob adds cheese
  cause: { "/": "bafyreistep3..." }             // Also based on Step 3
}
#+end_src

*What happens?*

1. Alice's transaction runs first
   - Checks: =WHERE fact = :cause= → matches ✓
   - =UPDATE memory SET fact = alice_fact WHERE fact = :cause=
   - ✓ Success, 1 row updated

2. Bob's transaction runs second
   - Checks: =WHERE fact = :cause= → NO MATCH! (memory now points to alice_fact)
   - =UPDATE memory SET fact = bob_fact WHERE fact = :cause=
   - ✗ Failure, 0 rows updated → *ConflictError*

Bob must:
- Fetch latest state (Alice's version)
- Merge changes (or choose conflict resolution strategy)
- Retry with new =cause=

This is *compare-and-swap* (CAS) semantics, preventing lost updates.

From the pattern/recipe perspective:

** Q5: Table Growth and Performance Impact

*** Growth Rate

The =fact= table grows at *1 row per operation*:
- Create: +1 row
- Update: +1 row
- Delete (retraction): +1 row
- No rows ever deleted (append-only)

*Formula:* =fact_rows = N_entities × (1 + avg_updates) + retractions=

*Examples:*

| Workload                  | Entities | Updates/Entity | Retractions | Fact Rows |

** Q7: Good Design Patterns to Maintain

*** Excellent Patterns Found

**** 1. Content-Addressed Storage

File: [[file:packages/memory/space.ts::67][space.ts:67-74]]

#+begin_src sql
CREATE TABLE IF NOT EXISTS datum (
  this TEXT NOT NULL PRIMARY KEY,  -- ← Merkle reference (hash of content)
  source JSON                       -- ← The actual JSON
);
#+end_src

*Why it's good:*
- Automatic deduplication (same content → same hash)
- Tamper-evident (changing data changes hash)
- Cryptographic integrity (can verify data matches hash)
- Efficient storage (share identical values)

*Example:* 1000 documents with =status: "pending"= store the string once.

**** 2. Immutable History

File: [[file:packages/memory/space.ts::80][space.ts:80-90]]

The =fact= table is *append-only*:
- Facts are never deleted (see all INSERT, no DELETE)
- Complete audit trail
- Enables time-travel queries
- Supports causality tracking

*Why it's good:*
- Debugging: "What was the state at timestamp X?"
- Conflict resolution: "Which changes came first?"
- Compliance: "Who changed what when?"
- Data recovery: "Undo this change"

**** 3. Compare-and-Swap Semantics

File: [[file:packages/memory/space.ts::146][space.ts:146-152]]

#+begin_src sql
UPDATE memory
  SET fact = :fact
WHERE
  the = :the
  AND of = :of
  AND fact = :cause;  -- ← CAS: only update if cause matches current state
#+end_src

*Why it's good:*
- Prevents lost updates in concurrent scenarios
- Optimistic concurrency (no locks needed)
- Forces client to acknowledge current state
- Detects conflicts immediately

**** 4. Separation of History and State

Three-table design:
- =fact= → Complete history (grows forever)
- =memory= → Current state (constant size)
- =datum= → Shared values (deduplicated)

*Why it's good:*
- Fast current-state queries (small =memory= table)
- Historical queries available when needed
- Storage-efficient (datum deduplication)
- Clear responsibility (each table has one purpose)

// packages/memory/space.ts - Safe approach

const initializeDatabase = (database: Database, address: URL | null) => {
  // These pragmas can be added without breaking existing databases:

  database.exec("PRAGMA foreign_keys = ON;");

#+begin_src typescript
const retryTransaction = async <T>(
  fn: () => T,
  maxRetries = 3
): Promise<T> => {
  let lastError;
  for (let i = 0; i < maxRetries; i++) {
    try {
      return fn();
    } catch (error) {
      if ((error as SqliteError).code === 5) {  // SQLITE_BUSY
        lastError = error;
        await new Promise(resolve => setTimeout(resolve, 100 * Math.pow(2, i)));
        continue;
      }
      throw error;  // Not a transient error
    }
  }
  throw lastError;
};
