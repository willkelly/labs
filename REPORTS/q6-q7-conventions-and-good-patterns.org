* Executive Summary

The packages/memory codebase implements a sophisticated content-addressed, immutable memory store using SQLite. While the design patterns are generally excellent (CAS semantics, prepared statements, transactions, schema migrations), several critical SQLite pragmas are missing that would significantly improve reliability, performance, and data integrity. The codebase also includes a workaround for concurrency issues in the Deno SQLite bindings that serializes all database operations.

* Q6: SQLite Conventions Being Ignored

** CRITICAL: Missing PRAGMA foreign_keys

*** The Problem
SQLite does NOT enable foreign key constraint enforcement by default. The codebase defines foreign key constraints in the schema but never enables their enforcement:

#+BEGIN_SRC sql
-- From space.ts line 87-88
FOREIGN KEY('is') REFERENCES datum(this)
#+END_SRC

*** Current State
File: ~/packages/memory/space.ts~ (lines 335, 370)
#+BEGIN_SRC typescript
database = await new Database(address ?? ":memory:", {
  create: false,
});
database.exec(PREPARE);  // ❌ No PRAGMA foreign_keys = ON
#+END_SRC

*** Impact
- Foreign key constraints are silently ignored
- Data integrity issues can occur without errors
- Orphaned records in ~fact~ table could reference non-existent ~datum~ records
- The careful schema design is undermined

*** Recommendation
Add immediately after database creation:
#+BEGIN_SRC typescript
database = await new Database(address ?? ":memory:", {
  create: false,
});
// CRITICAL: Enable foreign key enforcement
database.exec("PRAGMA foreign_keys = ON;");
database.exec(PREPARE);
#+END_SRC

** CRITICAL: Missing PRAGMA journal_mode = WAL

*** The Problem
The codebase does not enable Write-Ahead Logging (WAL) mode, which is essential for:
- Better concurrency (readers don't block writers)
- Better performance (fewer disk syncs)
- More reliable operation under concurrent load

*** Current Concurrency Workaround
File: ~/packages/memory/memory.ts~ (lines 67-77)
#+BEGIN_SRC typescript
/**
 * Runs task one at a time, this works around some bug in deno sqlite bindings
 * which seems to cause problems if query and transaction happen concurrently.
 */
async perform<Out>(task: () => Promise<Out>): Promise<Out> {
  return await traceAsync("memory.perform", async (_span) => {
    const result = this.ready.finally().then(task);
    this.ready = result.finally();
    await this.ready;
    return await result;
  });
}
#+END_SRC

The ~perform()~ method serializes ALL database operations to work around concurrency issues. WAL mode would likely eliminate or reduce this problem.

*** Evidence from @db/sqlite Library
The @db/sqlite library uses FFI (Foreign Function Interface) to call native SQLite, not WASM. This means it SHOULD support WAL mode, unlike WASM-based Deno SQLite packages which have file locking limitations.

*** Recommendation
#+BEGIN_SRC typescript
database = await new Database(address ?? ":memory:", {
  create: false,
});
database.exec("PRAGMA foreign_keys = ON;");
database.exec("PRAGMA journal_mode = WAL;");  // Enable WAL mode
database.exec(PREPARE);
#+END_SRC

Note: Skip WAL for ~:memory:~ databases as it's not applicable.

** HIGH PRIORITY: Missing PRAGMA busy_timeout

*** The Problem
File: ~/packages/memory/space.ts~ (lines 843-845)
#+BEGIN_SRC typescript
// SQLite transactions may produce various errors when DB is busy, locked
// or file is corrupt. We wrap those in a generic store error.
// @see https://www.sqlite.org/rescode.html
#+END_SRC

The code acknowledges that SQLite can fail with BUSY/LOCKED errors, but doesn't configure a busy timeout to handle contention gracefully.

*** Impact
- Transactions fail immediately if database is locked
- No automatic retry mechanism
- Poor behavior under concurrent load

*** Recommendation
#+BEGIN_SRC typescript
database.exec("PRAGMA busy_timeout = 5000;");  // Wait up to 5 seconds
#+END_SRC

This makes SQLite automatically retry for up to 5 seconds when encountering locks, rather than failing immediately.

** MEDIUM PRIORITY: Missing Performance Pragmas

*** PRAGMA synchronous
Default value is FULL, which is very safe but slow. With WAL mode, NORMAL is safe and much faster.

#+BEGIN_SRC typescript
database.exec("PRAGMA synchronous = NORMAL;");  // Safe with WAL mode
#+END_SRC

*** PRAGMA temp_store
Storing temporary tables in memory improves performance:

#+BEGIN_SRC typescript
database.exec("PRAGMA temp_store = MEMORY;");
#+END_SRC

*** PRAGMA cache_size
Default is usually too small. Consider increasing:

#+BEGIN_SRC typescript
database.exec("PRAGMA cache_size = -64000;");  // 64MB cache (negative = KB)
#+END_SRC

** EXCELLENT: Content-Addressed Storage

*** Implementation
File: ~/packages/memory/space.ts~ (lines 67-70)

- Merkle references provide cryptographic integrity
- Automatic deduplication (same content = same reference)

** EXCELLENT: Immutable History with Fact Table

*** Implementation

* Conclusion

The packages/memory codebase demonstrates exceptional software engineering with its content-addressed storage, immutable history, CAS semantics, and careful use of prepared statements and transactions. The schema design is well-thought-out with proper foreign key relationships and efficient indexes.

However, the missing SQLite pragmas represent a critical gap that undermines some of these design decisions:

1. **Foreign key constraints are not enforced** despite being carefully defined
2. **Concurrency issues** require serializing all database operations
3. **Performance** is likely suboptimal without WAL mode and tuned settings

The good news: these are easy fixes that don't require any schema changes or refactoring. Simply adding the recommended PRAGMA statements at database initialization would significantly improve reliability, performance, and data integrity while preserving all the excellent design patterns already in place.

**Recommended next steps:**
1. Add the critical pragmas immediately (foreign_keys, journal_mode, busy_timeout)
2. Test whether the perform() serialization can be removed after enabling WAL
3. Create a migration documenting these requirements
4. Add database health checks to verify pragma settings
