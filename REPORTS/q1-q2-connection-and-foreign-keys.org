* Executive Summary

This report investigates two critical aspects of SQLite usage in =packages/memory=:

1. *Q1 - Connection Management*: The =perform= method in =memory.ts= claims to work around "some bug in deno sqlite bindings" but this appears to be a *misconception about SQLite's concurrency model* rather than an actual bug in the Deno SQLite library.

2. *Q2 - Foreign Key Constraints*: Foreign keys are declared in the schema but are *NOT being enforced* because SQLite disables them by default and the code does not execute =PRAGMA foreign_keys = ON;=.

*Key Findings:*
- SQLite allows *multiple concurrent reads* but only *one write transaction at a time*, even in WAL mode
- Running queries and transactions concurrently on the *same connection* is problematic regardless of the library used
- Foreign key enforcement must be explicitly enabled per-connection and is currently disabled
- No tests validate foreign key behavior

** SQLite Concurrency Model

*** Core SQLite Behavior

SQLite's concurrency model has fundamental limitations:

1. *Multiple Readers, Single Writer*: SQLite allows multiple simultaneous read transactions but only ONE write transaction at a time
2. *Connection-Level Locking*: Locks are managed at the database file level, not the connection level
3. *Transaction Serialization*: Write transactions are inherently serialized, even in WAL mode

*** WAL Mode Benefits and Limitations

*WAL (Write-Ahead Logging) Mode:*
- Allows concurrent readers with one writer
- Readers don't block writers, writers don't block readers
- BUT: Still only ONE write transaction at a time

From SQLite documentation:
#+begin_quote
"WAL mode provides more concurrency as readers do not block writers and a writer does not block readers. Reading and writing can proceed concurrently. However, SQLite allows only one write transaction at a time."
#+end_quote

*** The Real Problem: Same-Connection Concurrency

The issue is NOT a bug in =@db/sqlite=, but rather a fundamental limitation:

*You cannot run a query and a write transaction concurrently on the SAME database connection.*

This is true for ALL SQLite libraries because:
1. SQLite is single-threaded per connection
2. Transactions acquire locks that affect the entire connection
3. Mixing reads and writes on the same connection during an active transaction causes lock contention

** How Transactions Work in =@db/sqlite=

File: =packages/memory/space.ts:865=

#+begin_src typescript
return execute(session.store.transaction(commit), session, transaction);
#+end_src

The =Database.transaction()= method:
1. Wraps a function in a SQLite transaction
2. Executes =BEGIN TRANSACTION= before the function
3. Executes =COMMIT= if successful, =ROLLBACK= if error
4. Serializes write operations automatically

** Would a Read Pool Help?

*Yes, a separate read connection pool would help* if:

1. The application has high concurrent read load
2. Writes are less frequent than reads
3. Read queries take significant time

*Benefits:*
- Multiple read connections can query simultaneously
- Write connection remains dedicated to transactions
- Better throughput for read-heavy workloads

*Implementation Considerations:*
- SQLite in =@db/sqlite= doesn't support WAL mode (a limitation)
- Without WAL, readers block writers and vice versa
- Connection pool only helps if queries are on different connections

*The =perform= method creates a sequential queue:*

#+begin_src typescript
async perform<Out>(task: () => Promise<Out>): Promise<Out> {
  // Queue task after current 'ready' promise
  const result = this.ready.finally().then(task);
  // Update 'ready' to wait for this task
  this.ready = result.finally();
  // Wait and return
  await this.ready;
  return await result;
}
#+end_src

This ensures operations run sequentially:
- =transact()= → waits for previous operation
- =query()= → waits for previous operation
- =close()= → waits for previous operation

** SQLite Foreign Key Behavior

*** Default: DISABLED

From SQLite documentation:
#+begin_quote
"Foreign key constraints are disabled by default (for backwards compatibility), so must be enabled separately for each database connection."
#+end_quote

*** Enabling Foreign Keys

Foreign keys must be enabled with:

#+begin_src sql
PRAGMA foreign_keys = ON;
#+end_src

*Important:*
- Must be executed for EACH connection
- Cannot be set persistently in the database file
- Not inherited by new connections
- Future SQLite versions might enable by default (but not yet)

* Conclusion

Both issues stem from misconceptions about SQLite behavior:

1. *Q1*: The "bug in deno sqlite bindings" is not a bug at all, but correct SQLite behavior. The serialization is a reasonable workaround for the architectural choice of using a single connection per Space, given SQLite's single-writer limitation.

2. *Q2*: Foreign keys are declared but not enforced because SQLite requires explicit enabling via PRAGMA. This is a real data integrity risk that should be fixed immediately.

The good news: Both issues are well understood and have straightforward fixes. The code is otherwise well-structured and the use of transactions shows good understanding of database semantics.
