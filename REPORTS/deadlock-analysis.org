* Executive Summary

The code at [[file:../packages/memory/provider.ts::504][provider.ts:504]] bypasses the =perform()= serialization queue to avoid a **genuine deadlock** that occurs when subscriber notifications try to query the database while a transaction is still holding the queue lock.

This is a **design flaw** in the architecture where synchronous subscriber notifications create a circular dependency with the queue-based serialization mechanism.

* The Deadlock Call Stack

** Step-by-Step Flow

#+begin_example
1. User → memory.transact(transaction)
   ↓
2. Goes through perform() QUEUE [LOCK ACQUIRED]
   ↓
3. Executes: space.transact(transaction)
   ↓
4. Transaction succeeds, returns commit
   ↓
5. Notify subscribers: for (subscriber of subscribers)
   ↓
6. Calls: subscriber.commit(result.ok) [WAITING FOR COMPLETION]
   ↓
7. provider.commit() runs
   ↓
8. Calls: getSchemaSubscriptionMatches()
   ↓
9. Wants to run: memory.querySchema() ← DEADLOCK!
#+end_example

* Why It Deadlocks

** The Circular Dependency

The problem occurs because:

1. *Step 2*: =perform()= queue has a LOCK (waits for current task to finish)
2. *Step 6*: Current task is WAITING for =subscriber.commit()= to complete
3. *Step 9*: =subscriber.commit()= wants to call =memory.querySchema()=
4. But =memory.querySchema()= goes through =perform()= queue (memory.ts:95-96)
5. =perform()= queue is BLOCKED waiting for step 2's task to finish
6. Step 2's task is WAITING for step 6 to finish
7. Step 6 is WAITING for step 9 to finish
8. Step 9 is WAITING for the perform() queue
9. **CIRCULAR DEPENDENCY = DEADLOCK**

* The Risk of This Bypass

** Race Condition Potential

This creates a **race condition** risk:

1. The query runs OUTSIDE the serialization queue
2. Could potentially run concurrently with another transaction
3. This is exactly what the =perform()= queue was designed to prevent!

** Why It Currently Works

The bypass is (probably) safe because:

1. *Read-only*: The query only reads, doesn't write
2. *Post-commit*: The write transaction has already committed (step 4 completed)
3. *SQLite allows concurrent reads*: Even without WAL mode, multiple readers are OK
4. *Queue still locked*: The =perform()= queue lock is still held, so no OTHER writes can interfere

** Fragile Dependencies

But it's fragile and depends on:

- The query being truly read-only
- The transaction having fully committed before subscribers are notified
- No other code paths bypassing the queue
- SQLite's read concurrency guarantees

* Root Cause: Architecture Design Flaw

** The Real Problem

The architecture has a fundamental issue:

#+begin_quote
*Subscriber notifications should NOT be synchronous*
#+end_quote

** Current Design (Problematic)

#+begin_src typescript
// BLOCKING on subscribers
for (const subscriber of subscribers) {
  await subscriber.commit(result.ok);  // ← Blocks transaction!
}
#+end_src

Problems:
- Transaction cannot complete until ALL subscribers finish
- Subscribers cannot query without deadlocking
- Creates tight coupling between transaction and notification
- Defeats the purpose of the serialization queue

** Better Design Option 1: Fire-and-Forget

#+begin_src typescript
// NON-BLOCKING, fire-and-forget
for (const subscriber of subscribers) {
  // Don't await! Let them run async
  subscriber.commit(result.ok).catch(err => logger.error(err));
}
// Transaction completes immediately
#+end_src

Benefits:
- No deadlock possible
- Transaction completes faster
- Subscribers can query freely
- Looser coupling

Drawbacks:
- No guarantee subscribers processed the commit
- Errors in subscribers don't fail the transaction
- Harder to test

** Better Design Option 2: Message Queue

#+begin_src typescript
// Post to a message queue
for (const subscriber of subscribers) {
  messageQueue.publish('commit', { subscriber, commit: result.ok });
}
// Subscribers consume from queue independently
#+end_src

Benefits:
- Complete decoupling
- Subscribers can retry on failure
- Can add rate limiting, backpressure
- Scalable

Drawbacks:
- More complex infrastructure
- Eventual consistency (subscribers notified async)

** Better Design Option 3: Separate Read Connection for Subscribers

#+begin_src typescript
class MemoryProviderSession {
  constructor(
    public memory: MemorySession,

  ) {}

  private async getSchemaSubscriptionMatches(...) {

    const result = await querySchemaDirectly(
      this.subscriberReadConnection,

  }

#+end_src

Benefits:
- Keeps synchronous notification pattern
- No deadlock (separate connection)
- Explicit about the special case

Drawbacks:
- More connections = more memory
- Requires WAL mode to be safe
- Doesn't solve the architectural flaw

* Implications for WAL Mode

** Current Situation (No WAL)

The bypass is relatively safe:
- Only one write at a time (enforced by =perform()= queue)
- Bypass query runs while queue is locked
- No other transactions can interfere
- Read concurrency is safe in SQLite even without WAL

** With WAL Mode + Read Pool

The bypass becomes *LESS safe*:

1. Multiple queries could run concurrently with the bypassed query
2. The bypassed query might read partial state if another write is in progress
3. Race conditions become more likely
4. Need more sophisticated synchronization

** What Must Happen Before Enabling WAL

Either:

1. *Refactor subscriber notifications to be async/non-blocking*
   - Remove the =await= in subscriber loop
   - Accept eventual consistency

2. *Give subscribers their own read connection*
   - Not shared with main connection pool
   - Dedicated to subscriber queries

3. *Add extensive testing*
   - Test subscriber notification path with concurrent queries
   - Verify no race conditions
   - Stress test with multiple subscribers

** Immediate Action

Document this extensively in the code:

* Conclusion

The bypass at =provider.ts:504= is:

- ✅ Necessary (prevents genuine deadlock)
- ✅ Well-documented (has comment explaining why)
- ✅ Isolated (only one bypass in entire codebase)
- ⚠️  Fragile (depends on specific timing and guarantees)
- ⚠️  Architectural flaw (symptom of synchronous subscriber design)
- ❌ Risk with WAL mode (becomes less safe with increased concurrency)

*Bottom line:* This is a clever workaround for a design problem. It works now, but is a ticking time bomb if concurrency increases via WAL mode. The proper fix is to make subscriber notifications asynchronous.
